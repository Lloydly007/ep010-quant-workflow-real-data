# 流程与工作流优化（本次实战复盘）

> 这份文档记录真实跑完一遍全流程时**实际踩到的 7 个坑**、落地机制、以及下一版该改什么。
> 所有数字都来自本次运行，不是设想。

---

## 一、七个坑与对应机制

### 1. 数据抓取：单会话 20.5 秒/股，8 并发直接被封

**现象**：BaoStock 单会话抓 1,545 只要 8.8 小时；改 8 进程并发后，10 秒内被拉黑（`黑名单用户`），8 个分片合计只拿到 71 只。

**结论**：拉黑的是 **IP**，不是账号（换 VPS 出口 IP 立刻能登）。

**机制**：
- 抓取一律**多出口 IP、每 IP 单会话**（本次用 5 台 VPS 的 SSH 隧道，各 1 条）；
- 关键参数 `--codes-file / --shard / --nshards / --bs-ip / --bs-port`，让分片可任意切；
- **进度必须可见**：`print(..., flush=True)` 每 25 只一次。本次前 2 小时因为 print 被块缓冲，完全看不到进度，只能靠 `py-spy dump --locals` 读循环变量 `i`。

### 2. 内存泄漏：每份配置涨 100~150 MB，`gc` 完全无效

**现象**：单进程连跑 60 份配置，RSS 从 552 MB 涨到 6,717 MB；加 `gc.collect()` 后曲线一模一样。

**结论**：泄漏在 numpy/pyarrow 的 C 层 arena，Python 的 gc 管不到。4 worker 各带一份面板副本，跑到 7.2 GB/进程就把 32 GB 吃光。

**机制**：
- **分块进程**：每 60~100 份换一次进程，内存随进程退出归零（`tools/farm_chunked.py`）；
- 并发按 **内存** 定，不按 CPU 定（8 worker × 3.4 GB ≈ 25 GB 是这台机器的上限）；
- 用 `tools/mem_growth.py` 先量斜率再定块大小，不要拍脑袋。

### 3. multiprocessing.Pool 死锁：CPU 归零但进程都还在

**现象**：`layers --formal` 跑到 140/146 停住。py-spy 显示 worker 全停在 `queues.get()`、父进程停在 `pool.py:861 next()`，15 秒内消耗 CPU **0.0 秒**，台账 40 分钟没写一行。

**结论**：只要有一个 worker 非正常退出（如 OOM），父进程就会永远等一个不会来的结果，**不报错、不崩溃**。

**机制**：
- 所有长跑任务必须带**卡死检测**：盯 `ledger/ledger.csv` 的修改时间，N 分钟不动即杀进程重来（`tools/layers_robust.ps1`）；
- 重启是安全的：每算完一个探针落一行台账，重启后自动从断点继续；
- 阈值：3 分钟（正常几十秒一行）。

### 4. 后台作业被会话回收：`Start-Process` 也不够

**现象**：农场、两个工作流、一个回测链，先后 3 次在会话重启时被一起杀掉——`job_list` 里直接变成 `unknown job`。

**结论**：`Start-Process` 仍在会话的 job object 里；会话回收会整棵树带走。

**机制**：
- 长任务用 **WMI 创建进程**（`Invoke-CimMethod -ClassName Win32_Process -MethodName Create`），挂到 WMI 提供程序下，脱离作业对象；
- 或者：启动进程的那条命令**立刻退出**，让子进程变成孤儿（本次抓取分片就是这么活过 2.5 小时的）；
- **不要用长阻塞等待**（`Start-Sleep 600`）来等任务，那会把自己变成问题的一部分；改为定时短查询轮询。

### 5. 形态错误：一份基于 30 只试点的结论污染了 200 份配置

**现象**：第 1~2 轮 10 个 agent 全写成 rule 型（买卖规则），A 路 L2 通过率 0% / 6%。原项目 92%~98% 是 score 型，它唯一活过 L6 的三席全是 score 型。

**根因**：因子清单里写着「30 只池 + holdings 30 ⇒ 打分型等于全池等权、选股失效」。那是试点池（30 只）的推论，在 1,545 只上不成立，但它被 10 个 agent 当成事实，集体避开了唯一正确的形态。

**机制**：
- **文档里每一条定量结论必须带样本前提**（`[样本: 30 只试点 / 2013-2024]`），没有标签的定量结论视为待验证；
- **每轮工作流加一道"形态自检"机器门**：写完统计 `type` 分布，与目标形态（如 score ≥ 80%）不符直接打回重写；
- 新研究的第 1 轮应先读原项目的样例形态分布，再定提示词。

修正后效果：score 型 L2 通过率 A 80.5% / B 84.2%，原项目 72.2% / 80.6%。

### 6. 重复回测：看门狗重起把 12,000 份跑成了 59,000 行

**现象**：台账 59,461 行猴子记录，唯一配置只有 12,000 个——平均每个配置被跑了 5 次。

**结论**：`filter_pending` 只按 `status=ok` 判重；重启后重扫 seed 目录时没有完全挡住。

**机制**：
- 统计一律按 `(config, start, end)` 去重取最新行，**DSR 的 N 按唯一配置计，不按行数计**；
- 报错行（`error_runtime`）不计入筛选失败，但必须留在台账（append-only）；
- 重启前先跑一次 `progress.py`，确认到底还有多少没跑。

### 7. 口径漂移：同一件事写了三遍，三遍都不一样

**现象**：
- 年化按 365 日历日算，引擎按 250 交易日 → 图上比报告高 0.4~0.7pp；
- 封存期 424 天（逐对象）与 436 天（组合含 ETF 延长）混用；
- 基准一会儿叫「池等权」一会儿叫「510300」（引擎里两个都有，含义不同）。

**机制**：
- `tools/meta.py` 作为**口径单一事实来源**（数据段、年化基数、基准代码、门槛、预期值）；
- `tools/verify_report.py` 作为**报告数字回源门**：把报告里的关键数字逐条回查 JSON/台账，不一致就 exit 1。本次它实际抓出了两处（B 路 82.2% 应为 84.2%、负号用了 U+2212 导致比对失败）；
- 报告改数必须重跑这道门，不能靠人眼。

## 二、下一版流程（建议）

```
[0] 环境自检   并发按内存定（不是 CPU）、磁盘、口径常量
[1] 数据抓取   多出口 IP 单会话 + 分片 + 断点续传 + 逐 25 条 flush
[2] 合并校验   并用集/去重/封存期泄漏检查，不达标拒绝写盘
[3] 因子清单   每条定量结论带样本标签；写明主力形态与目标占比
[4] 每轮搜索   agent 写 → 机器门（load_config）→ 形态门（type 占比）→ 结构去重门
[5] 回测       分块进程 + 卡死检测 + 台账按唯一配置去重统计
[6] 漏斗       layers_robust（死锁自愈）→ 共同池终判
[7] 入围/冻结  记录 SHA256，开封前不得改
[8] 开封       OPEN_SEALED 标记 + 一次性评估 + 无论成败立刻移除
[9] 报告       生成 → verify_report 回源 → 才允许交付
```

新增的两道门（[4] 的形态门、[9] 的回源门）是本次最贵的两条教训换来的。

## 三、仍然没解决的

1. **数据缺口是硬伤**：缺中证1000 小盘池、缺财务（ROE）、缺龙虎榜/两融/北向。强度差 3~6pp 的根因在这里，流程优化解决不了。
2. **三席同质**：本次三席日收益相关 0.992~0.995，实际是同一策略的三个变体。下一版应在生成阶段就**强制因子分散**（每席至少一个不共用的因子腿），否则"三席"没有分散意义。
3. **缺强风格基准**：无法判断超额是真选股还是 size/value/turnover 三因子暴露。这是下一个最该补的验证。
4. **池是历史并集**：含后期调入者，不是逐日可得成分；原项目也承认这是近似。
