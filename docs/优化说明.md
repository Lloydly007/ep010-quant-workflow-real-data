# v2 优化说明：工作流 + 缺口 + 差异

v1（`ep010-research/`）是对 EP010 的第一次复刻：引擎原样、每路 2 轮 × 24 配置。
六个独立审计角色在 v1 上找出 7 条硬问题，其中 6 条是**引擎缺口**；规模上也只做到原版规格的 1/5。

v2（本目录）做三件事：

1. **修引擎缺口**（6 处，可幂等重放）：`tools/apply_engine_patches.py`
2. **用机器证明"修完不改结果"**：`tools/regress_50.py` → 50 个配置逐位一致
3. **补规模与工作流**：每路 6 轮 × 39 配置（A 204 / B 180 / 主随机 204 / 农场 20 × 204），
   每轮之间都由父级跑门（`config.py` → `run_batch` → 台账），agent 从台账读下一轮

数据与 v1 **逐字节相同**（`data/raw/daily.parquet` 哈希一致），所以 v1→v2 的差异只来自代码与搜索规模。

## 1. 六个补丁（P1~P6）

| 编号 | 缺口（v1 实测证据） | 修法 | 验证 |
|---|---|---|---|
| P1 | `find_config_yaml` 的索引只在首次调用时构建；`farm` 先建索引再写配置单 → 20 个种子的 L5 全部「找不到原配置单」 | 加 `refresh_config_index()`，写盘后调用 | v1：62 条该错误；v2：0 |
| P2 | `canonical_config()` 把唯一的 `name`/`desc` 纳入比较键 → rules 第 11 章的去重是空操作 | 归一时剔除 `name`/`desc` | v2：204 个猴子配置 → 204 个不同结构 |
| P3 | 市场级零件 `etf_above_ma_n` 可作因子/排序键/嵌套基零件，截面秩恒并列 → 零信息组合过 L1~L5 | 解析期拒绝并给指引 | v1：`m43_028` 进入围名单；v2：0 个 |
| P4 | 上述配置回测时抛 `KeyError('close_adj')`，不可诊断 | 抛带指引的 RuntimeError | v1：`m43_026` 一例 |
| P5 | L5 的「空邻域空真通过」无任何标记，报告无法注明检验范围（rules 5.2） | `l5_detail` 记录 `empty_neighborhood` | 漏斗报告可点名 |
| P6 | 随机配置生成器的因子池含市场级零件（P3 的源头） | 因子池剔除 | v2：0 个这类配置 |

补丁全部集中在 `engine/funnel.py`、`engine/config.py`、`engine/operators.py` 的
**解析/记录路径**，不碰任何撮合、指标、筛选阈值。

## 2. 逐位回归（rules.md 第 12 章）

`tools/regress_50.py`：从 v1 台账分层抽 50 个已成功配置（覆盖 A/B/主随机/邻域探针），
在 v2 的同一份数据上重跑，比对 27 个数值列，**零容差**（缺失与 NaN 视为同一缺失，
其余按双精度逐位相等）：

```
50 / 50 逐位一致；被 P3 拒绝 0 个
```

明细 `reports/regress_50.md`。这条门是"改引擎"能不能被接受的前提：**没动到的东西必须一位不变。**

## 3. 工作流：从"两批 agent"到"六轮带门"

v1 的编排是两段式（提案 → 落地），每段一个 barrier。v2 改成**六轮循环**，每轮：

```
workflow 段（6 个 agent：A 组 3 个 + B 组 3 个，各写 13 个配置单）
        ↓  父级机器门：engine/config.py × 78 → engine/run_batch.py --group A / --group B
        ↓  tools/round_digest.py 生成下一轮的台账摘要（顶层 IR、零成交清单、零件覆盖）
下一轮 prompt（摘要 + 本轮侧重 + 四类动作配额）
```

相对 v1 的四个改进：

1. **修复回路**：每轮 gate 都会跑 `config.py` 全量校验；v2 的 468 个配置 **0 个被拒**
   （agent 自校验闭环生效）——v1 曾出现 0 成交与跑不起来的配置。
2. **反馈来自机器**：下一轮 prompt 里的"谁强谁弱"由 `round_digest.py` 从台账算出来，
   不是父级或 agent 的转述。
3. **动作配额**：每轮强制四类动作（参数邻域 / 跨族重组 / 修失败模式 / 新方向）各 ≥3 个，
   避免六轮都在刷同一个动量。
4. **给 L5/L7 留路**：第 4 轮起明确要求"低相关优先于继续刷 IR"，第 6 轮要求给头部造**真邻域**
   （打分型的 L5 邻域只由 factors 的窗口 n 产生，`xsec_pct` 包裹会把窗口藏进 `of`）。

| 编号 | 缺口 | 修法 | 验证 |
|---|---|---|---|
| P13 | rules 第 1 章的"搜索角色不得读验证期"在代码层只是 P9 的**可选环境变量**，默认不拦 | 给搜索角色的唯一入口 `run_batch.py` 加 `--role`，**默认 search**：不带参数就只能跑搜索期；`--role owner` 才放行。同时把 `guard.ROLE` 一起改（它是 import 时读的，只改 env 无效——第一版就栽在这） | 实测：`run_batch --start 20230101` 被拒（退出码 2，一行中文说明）；加 `--role owner` 正常跑完 50 个配置 |

## 7. 规模差异：量化，而不是含糊过去

"每轮 39 个配置 vs 原版 100~150"这条差异，之前只是个数。`tools/scale_plan.py` 用
`run_backtest(record=False)` 实测单配置耗时（不写台账），再按本次实际结构（6 轮 × A/B + 主随机 + 20 组农场 + L5 邻域）
外推，写进 `reports/规模与成本.md`：

| 每轮配置数 | A/B 每路 | 基础回测数 | L5 邻域 | 总回测数 | 预计工时 |
|---|---|---|---|---|---|
| 39（本次） | 234 | 1,287 | 4,716 | 6,003 | 0.7 小时 |
| 60 | 360 | 1,980 | 7,254 | 9,234 | 1.3 小时 |
| 100 | 600 | 3,300 | 12,090 | 15,390 | 2.2 小时 |
| 150 | 900 | 4,950 | 18,135 | 23,085 | 3.4 小时 |

结论：**回测不是瓶颈**（原版规格也就 2~3 小时），真正的成本在 agent 侧（每轮 100+ 个 YAML 需要 8~10 个 agent，
6 轮 A+B 上百个会话）。所以这次的规模是"有依据的取舍、可继续扩"，不是做不到。

## 8. 还没修的（诚实清单）

1. **验证期隔离的边界是"谁在跑"**：P13 让搜索入口 `run_batch` 默认拒绝验证期，
   但 `funnel.py`/`portfolio.py` 在进程内直接调 `run_backtest`（L6、组合层本来就要读验证期）。
   这是设计使然，不是漏洞——但"隔离"仍依赖调用方选对入口，而不是数据层强制。
2. **`MemoryError` 的触发点仍没定位到具体分配**：P14 降并发 + P15 单进程重试把损失控制住了
   （失败任务会被重跑而不是永久丢失），但"哪一步峰值最高"还没测到。
3. **行情是合成的**：结论只对"流程与机器裁决"有效，不构成 A 股实证。
4. **报告/PPT/Excel 由脚本渲染**：数字全部来自 `data/*.json` 与台账，但脚本本身还没有
   独立审计角色逐句核过（v2 的审计 D 核过一轮，找出并已修掉一处把 v1 事实写进 v2 报告的错）。

### 9.2 内存：根因找到并修掉

`tools/mem_probe.py` 用 tracemalloc 量出：

| 阶段 | Python 堆 |
|---|---|
| 引擎 import 完 | 0 MB |
| 载入共享面板（memmap） | 26 MB |
| 跑一个 23,422 笔的配置 | +98 MB（峰值 124 MB） |

所以**面板不是问题**（memmap 是文件页、跨 worker 共享），峰值来自单配置回测内部。
`monkey_11` 那 98 条 `MemoryError` 的根因是**冷启动竞态**：共享面板缓存还没发布时，
每个 worker 各自 `DataStore()` 建一份 pandas 面板（比 memmap 大 10~20 倍），10 个 worker 同时建就爆。

- **P16**：`make_runner` 在起 worker 池**之前**先在父进程把缓存建好；worker 只剩 memmap 挂载。
  同时把 `WORKER_MEM_GB` 从"拍脑袋的 2.5"改成实测口径 1.2（10 worker + 父进程实测 16.1GB）。
- **P17**：P12 需要"基础配置结构签名"，原实现在 layers/farm 里被调 25 次以上，每次重读几千个
  YAML——600×20 规模下直接把堆吃光（`read_csv` 报 out of memory，其实是前面耗尽的）。
  改为进程内算一次并缓存。

修完后 12,000 个配置的农场跑完 **0 条 MemoryError**（修之前是 98 条）。
